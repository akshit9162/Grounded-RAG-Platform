01

Ingest

ingestion/chunker.py

Documents are split into overlapping, token-aware chunks — not entire files — so the retriever can return the specific paragraph that answers a question, not a whole document. Splitting respects paragraph and sentence boundaries first, falling back to hard token cuts only for pathological unbroken text.

Overlap between neighboring chunks prevents a clause from being cut in half at a boundary and losing meaning on both sides. Chunks are pushed through an in-process queue by default, or a Kafka topic in production — same chunker, different transport.

CHUNK_SIZE_TOKENS=350
CHUNK_OVERLAP_TOKENS=60
local in-process queue → prod INGESTION_TRANSPORT=kafka

Overlapping chunks

Each bar is one chunk of refund_policy.txt. The overlap zone means a clause spanning a boundary still appears whole in at least one chunk.

02

Retrieve — hybrid search

retrieval/hybrid.py

Dense embeddings catch paraphrased questions ("money back" ≈ "refund"), but miss exact tokens — order IDs, SKUs, error codes. BM25 keyword search catches those exact tokens, but misses paraphrase. Neither alone is enough, so both run on every query.

The two ranked lists are merged with reciprocal rank fusion (RRF), not a raw weighted-score blend — dense cosine scores and BM25 scores live on incompatible scales, so fusing on rank position instead of raw score is the standard, defensible way to combine two heterogeneous retrievers.

DENSE_TOP_K=20
BM25_TOP_K=20
local TF‑IDF embeddings → prod EMBEDDING_MODEL=BAAI/bge-large-en-v1.5
local in-memory vectors → prod VECTOR_STORE_BACKEND=qdrant

Fusing two rankings by rank, not score

dense (cosine)
rank 1 chunk #4
rank 2 chunk #2
rank 3 chunk #6
⇄
bm25 (keyword)
rank 1 chunk #2
rank 2 chunk #4
rank 3 chunk #1
score(d) = Σ 1 / (60 + rank + 1) — chunk #2 and #4 rank highly in both lists and win the fusion; chunk #1 survives only through keyword match; chunk #6 barely clears.
03

Rerank

retrieval/reranker.py

The fused candidates are still ranked by two cheap, independent scoring functions. A reranker looks at the actual query and each candidate chunk together and re-scores relevance directly — far more accurate, and affordable now that it's only scoring a handful of survivors instead of the whole corpus. This is usually the single biggest lever on answer quality, and the step most beginner RAG projects skip.

Only the top RERANK_TOP_K chunks after this step go on to generation.

RERANK_TOP_K=3
local lexical overlap + relevance floor → prod RERANKER_MODEL=BAAI/bge-reranker-base

The fallback reranker also drops anything scoring below a small relevance floor — see lesson 02 for why that floor quietly affects an eval metric.

04

Generate — Claude, with forced citations

generation/llm.py + prompts.py

The top-ranked chunks are handed to an LLM behind a narrow LLMClient interface, with a system prompt that requires every claim to cite a chunk index like [2]. This isn't a style choice — it's what makes the guardrail stage possible: an answer can only be checked for grounding if it says which source it's grounded in. By default, that LLM call goes straight to Claude over the Anthropic API.

The actual API call

default ANTHROPIC_API_KEY set → real Claude (claude-sonnet-5)
no key → zero-dependency extractive mock, clearly labeled [extractive]
LLM_PROVIDER=vllm → self-hosted open-weight model via an OpenAI-compatible vLLM/TGI server

System prompt (the four rules)

1. Answer ONLY using the supplied excerpts — no outside knowledge.
2. Cite the excerpt number after every claim, e.g. [1] or [2][3].
3. If the excerpts don't contain the answer, say so exactly —
   "I don't have enough information in the available sources to answer that."
4. Be concise; don't repeat excerpts back verbatim at length.
05

Guardrail — is it actually grounded?

generation/guardrails.py

Citing a source doesn't guarantee the claim is true to it. The guardrail re-reads the answer against only the chunks it cited — first checking citations exist at all, then checking, sentence by sentence, whether each sentence's vocabulary actually overlaps the cited source. One fabricated sentence buried in an otherwise-solid answer can hide inside a whole-answer average — scoring per sentence is what catches it.

Q — What's your refund policy for digital goods?
A — Digital goods are non‑refundable once downloaded [2]. Standard physical orders can be returned within 30 days of delivery [1]. All refunds are processed within 2 business hours [2].
is_grounded: false
unsupported_sentences: 1

The flagged sentence cites [2], but "processed within 2 business hours" doesn't appear anywhere in that chunk — invented specificity riding on a real citation. The first two sentences pass individually; the guardrail still fails the whole answer, because one ungrounded claim is enough. This exact scenario is a regression test — see Tests.

Illustrative example, shaped to match this repo's sample corpus and guardrail logic — not a live call.

FAITHFULNESS_THRESHOLD=0.5
SENTENCE_FAITHFULNESS_FLOOR=0.2
reason codes: no citations · low overlap · unsupported sentence · honest refusal

Worth being precise about what this does not do: it detects an ungrounded answer after generation finishes — it doesn't stop the model from writing it, or stop the API from returning it. A caller has to check is_grounded and decide what happens next.

06

Serve

serving/app.py · auth.py · cache.py

A FastAPI layer wraps the whole pipeline behind three endpoints. Every request is API-key gated with a sliding-window rate limit. A semantic cache sits in front of generation — it matches on embedding similarity, not exact string match, so a rephrased question can still hit the cache instead of paying full pipeline cost again.

RATE_LIMIT_PER_MINUTE=60 / key
CACHE_SIM_THRESHOLD=0.95
CACHE_TTL_SECONDS=3600
local in-memory cache → prod CACHE_BACKEND=redis

POST/queryx-api-key

0.97 ≥ 0.95 → hit

07

Observe — every request, timed

observability/tracing.py

Every request is wrapped in named spans — one per pipeline stage — capturing duration and stage-specific metadata (which chunks were retrieved, their rerank scores, the guardrail verdict). Written as JSONL to data/traces.jsonl by default, so a slow or wrong answer can be traced back to the exact stage that caused it.

The span shape maps directly onto OpenTelemetry spans, so moving to real tracing infra (Arize Phoenix) is a matter of where spans are sent, not what they contain.

local JSONL file → prod OTEL_EXPORTER_OTLP_ENDPOINT → Arize Phoenix

Bars are scaled to the slowest span. generate — the network round-trip to Claude — dominates total latency, exactly as expected for an API-backed LLM call.

08

Evaluate — retrieval and generation, scored separately

evaluation/ragas_eval.py

A single end-to-end score can't tell you which stage regressed. This harness scores retrieval quality (context_precision, context_recall) independently from generation quality (faithfulness, answer_relevancy) — using real RAGAS + an LLM judge, or a dependency-light lexical-overlap proxy for fast iteration.

Three things debugging this taught

01

Isolate the layer

A wrong citation looked like a retrieval bug. It wasn't — the mock LLM's crude tokenizer failed to match "order" against "orders." scripts/debug_retrieval.py exists specifically to check retrieval's output before generation touches it.

02

A metric drop isn't always a regression

context_precision fell after upgrading the reranker. The reranker wasn't worse — the metric is document-level and rank-blind, and a 6-chunk demo corpus was too small for it to mean much. Fixed by tuning RERANK_TOP_K down to match the corpus size.

03

Check the full chunk, not the preview

A long, detailed answer looked fabricated — the API's citation preview truncates each chunk to ~200 characters. The source document was genuinely that detailed. Always verify grounding against full chunk text, never a truncated preview.
